# F054 实施设计

## 决策

- 智能体及工作流状态服务统一调用 application_publication；旧工作流 metadata 接口的 status 字段也委托状态服务，避免分叉。
- 工作流列表上下线直接调用状态接口，与内部共用；避免 metadata 更新接口再次加载详情与查询 visible，也避免列表中过期的名称/描述被作为修改提交。
- 用户组由业务侧既有 DAO 查询并核验应用租户；权限 application 只接收已验证目标与组 ID，不读取业务表。
- 使用标准 viewer 模型，自动来源记为 OTHER + `app_publish:<type>:<id>:group:<id>`。手工 USER_GROUP 来源拥有不同 fingerprint，撤销自动来源不会误删手工授权。
- 发布/下线动作授权是自动权限变更的前置条件；内部使用 F048 GrantService 持久化操作与 projection ledger，不要求操作者额外拥有 manage_permission。
- 当自动与手工来源投影到同一主体时，来源增加/删除可能没有 tuple 差异。仅允许非空业务变更的 resource GRANT_MUTATION 使用空 tuple 计划，仍保留操作账本、版本围栏、状态转换、SQL finalize 与恢复校验；跳过不必要的 OpenFGA 空读写。其他操作仍要求原子 COMMIT。
- 每批至多 20 个来源变更，避开 OpenFGA 90 tuple 原子上限；每批重新解析资源权限版本，使用基于版本与目标组集合的幂等键。处理全部批次后才更新应用状态。
- 再次上线先批量读取已撤销来源，复用持久化 ID 并递增当前版本；SQL prepare 校验同 ID 的版本，禁止旧版本恢复。权限与可见性计划在持久化前使用同一新版本，避免第二次上线时可见来源被错误退休。
- 复用业务侧已解析的操作者；通过 publish/unpublish 后构建系统授权变更上下文，跳过无关的 manage_permission 等级查询。最后一批依据已完成的 Grant after-state 判断同步结束，不再执行完整的空查询轮次。
- 可见来源 prepare 与 finalize 的 canonical owner 查找均批量读取，每次最多 500 个 fingerprint/ID，保留租户、来源身份、版本与投影状态校验。53 个来源对应的两处读取由各 53 次 SELECT 降为各 1 次。
- Redis 锁在不同 API 实例间序列化同一应用的相反上下线操作。业务操作时间上限短于锁租约，防止并行交错导致在线应用无默认查看权限。
- 构建列表请求 visible，不使用 managed/edit 筛选；所有写入口继续按具体动作判断，卡片上的当前版本选择也须 edit。
- 查看者复用原有智能体与工作流编辑界面，保留节点、配置、复制、导出及本地交互；不替换成简化画布。写按钮和持久化回调按具体动作校验权限，原应用内容不被保存。
- 工作流版本管理、离开保存提示与节点校验从超长 Header 中抽成独立 hook。查看者切换版本仅 GET，不调用 updateVersion；离开不触发保存提示或另存流程。版本重命名、删除仍按 edit 控制。
- 沿用后端写动作检查；入口不调用旧的编辑权限检查接口。智能体不再挂载查看者的“修改后保存并重启”遮罩，提示词支持选择、复制及本地更改。
- 前端上下线处理中立即禁用按钮/开关，并同步阻止重复调用；保存或发布失败时不继续上线、不切换卡片状态，恢复后可以重试。智能体上线成功立即跳转，取消固定 1.2 秒延迟。

## 已知边界

- 多批授权与业务状态更新不是单个分布式事务。中途故障返回错误；已经完成的 Grant 批次有持久化记录，重试按现有来源补齐/撤销，不重复创建。应用状态仅在所有权限批次成功后修改。
- F048 projection 的失败关闭与修复遵循既有运行时机制；本功能不新增绕过或恢复旁路。
- 自动授权针对上线时现有用户组。新增组及历史在线应用没有后台补授权任务。
- 修改现有权限领域对象通过 F048 服务进行，领域所有权仍归 F048。

## 验证

权限来源去重、重叠手工授权保留、操作者变化后的撤销、超过单批上限、无组及租户边界；前端查看者进入原编辑器、保存与版本写入受限、可浏览版本且不自动保存；仓库 lint/typecheck、后端单测及架构守卫。
